## 一、为什么改成统一网关

旧版本桌面入口用 `protocol: http` + `port: 8765` 的**端口服务**。飞牛拼接入口 URL 的规则是 `{protocol}://{当前浏览器 hostname}:{port}{url}`，于是：

| 登录桌面的方式 | 结果 |
| --- | --- |
| `http://192.168.x.x` 内网 | 正常 |
| `https://域名` 或自签证书 | iframe 里的 `http://` 被浏览器当 mixed content 拦掉，表现为「点了没反应」 |
| FN Connect / 外网域名 | 8765 不经中继转发，端口无法到达 |

统一网关把这条链路改成：

```
浏览器（任意网络、任意协议）
  → https://<当前飞牛域名>/app/edge-bookmarks
  → 飞牛 fnOS 校验 NAS 登录会话
  → 转发到 /var/apps/edge-bookmarks/target/app.sock（Unix Socket）
  → 应用服务
```

因为路径挂在**当前访问域名**下，HTTP / HTTPS / 内网 / 外网 / FN Connect 全都走同一套地址，不再需要为桌面单独开放或映射 8765。

## 二、四处必须对齐的配置

| 位置 | 值 | 作用 |
| --- | --- | --- |
| `fpk/app/ui/config` → `gatewayPrefix` | `/app/edge-bookmarks` | 注册公开路径 |
| `fpk/app/ui/config` → `gatewaySocket` | `app.sock` | 只写文件名，不写绝对路径 |
| `fpk/cmd/main` → `EB_GATEWAY_SOCKET` | `${TRIM_APPDEST}/app.sock` | 服务端实际监听的 Socket |
| `fpk/cmd/main` → `EB_GATEWAY_PREFIX` | `/app/edge-bookmarks` | 后端剥离前缀、注入前端 `<base>` |

`TRIM_APPDEST` 即 `/var/apps/edge-bookmarks/target`，所以 Socket 最终落在 `/var/apps/edge-bookmarks/target/app.sock`，与官方示例一致。

`cmd/main` 在 `start` 前会 `rm -f` 陈旧 Socket、`stop` 时再清一次，避免重启时 `Address already in use`。Socket 权限设为 `0660`（应用用户 + 网关所属组）。

服务端启动时：

- 恒起 **TCP 8765**（`DirectServer`）——给浏览器插件用；
- 有 `AF_UNIX` 时再起 **Unix Socket**（`GatewayUnixServer`）——给统一网关用；
- 两个通道共用同一个 `Store`、同一个 `Handler`，数据完全一致；
- Windows / 精简 Python 无 `AF_UNIX` 时自动降级为仅 TCP，不影响本地回归（用 `--gateway-test-port` 模拟网关通道）。

## 三、两条通道的职责边界（最容易踩的坑）

| | 桌面 Web 界面 | 浏览器插件 |
| --- | --- | --- |
| 地址 | `https://<飞牛域名>/app/edge-bookmarks` | `http://<NAS IP>:8765`（或外网备用地址） |
| 鉴权 | 飞牛 NAS 登录态 + 应用账号密码 | 应用账号密码换取的 Bearer 会话令牌 |
| 是否需开放 8765 | **不需要** | **需要**（或走网关 / 反代） |
| 内外网 | 自动，同一个域名 | 靠主/备地址自动切换 |

**关于网关地址**：统一网关在转发到 Socket **之前**会校验 NAS 登录会话。v1.2.1 起插件请求带 `credentials: 'include'`，能复用浏览器里已登录的飞牛会话，因此 `/app/edge-bookmarks` 也可以作为候选地址；但若浏览器未登录 NAS，网关会返回 `text/plain` 的 `invalid token`，插件会判失败并自动降级到局域网直连。

因此管理界面显示的「插件主地址」默认是**当前管理页地址**（网关模式下即 `/app/edge-bookmarks`），候选列表里同时给出局域网 IP + 8765 与其它可用地址，由插件逐个探测。

**例外：反代路径**。若你在飞牛登录地址上加了一条独立的反代 location（如 `/eb-api`），它绕开应用网关鉴权、直接转发到 `127.0.0.1:8765`，插件就可以填 `https://<飞牛登录地址>:<端口>/eb-api`——内外网只记一个地址。这不是「让插件走网关」，而是给插件开了一条同域名的新路径。服务端自动识别前缀并注入页面 `<base>`。完整配置见 [反向代理与统一登录地址](反向代理与统一登录地址.md)。

| | 桌面 Web 界面 | 浏览器插件（默认） | 浏览器插件（反代） |
| --- | --- | --- | --- |
| 地址 | `…/app/edge-bookmarks` | `http://<NAS IP>:8765` | `https://<飞牛登录地址>/eb-api` |
| 鉴权 | NAS 登录态 + 应用账号 | Bearer 会话令牌 | Bearer 会话令牌 |
| 8765 需对外可达 | 否 | 是 | 否（仅 NAS 内部转发） |
| 内外网 | 自动 | 主/备地址切换 | 自动（同一个地址） |

## 四、「自动识别内外网」具体做了什么

### 桌面侧

由统一网关天然完成：无论从内网 IP、HTTPS 域名还是 FN Connect 登录，URL 都是当前域名下的 `/app/edge-bookmarks`，且飞牛已校验登录态。Web 界面启动时会请求 `api/v1/setup/state`，发现 `gatewayAuth: true` 就显示当前 NAS 用户名，**但仍需再输入应用账号密码**。

### 插件侧

插件设置页只需两步：**① 粘贴从管理端复制的配置**（含主地址、备用地址、候选地址、账号，不含密码）→ **② 输入应用密码**。不再需要手工判断网络环境。

每次同步的端点选择逻辑：

1. 若 `activeEndpoint` 缓存未超过 5 分钟，直接用它；
2. 否则按顺序探测 `/api/v1/health`：**上次可用地址 → 主地址 → 备用地址 → 其余候选**（每个 3.5 秒超时），第一个返回 `{"ok":true}` 的胜出；
3. 胜出结果写入 `chrome.storage.local`，弹窗与设置页显示当前命中的地址；
4. 若请求过程中出现网络类失败，清掉缓存重新探测并重试一次——从内网切到外网（或反向）时无感切换；
5. 若所有地址都不可达，**逐条列出实际请求的 URL 与失败原因**（超时 / HTTP 状态 / 返回非 JSON），并对误填 `/app/...` 网关地址给出针对性提示。

「测试连接」会强制重新探测，并显示本次命中的通道。修改任一地址后缓存立即失效。

> 插件不会去猜自己是不是在内网，也不需要浏览器位置权限——它只判断「哪个地址此刻能连通」，这比判断网络环境更可靠。

### 备用地址怎么准备

插件外网访问需要一个**可达的 TCP 8765**（走网关或反代时则不需要对外暴露）：

| 方式 | 示例 |
| --- | --- |
| **飞牛登录地址 + 反代路径（推荐）** | `https://nas.example.com:9443/eb-api`，同一个地址内外网通用；见 [反向代理与统一登录地址](反向代理与统一登录地址.md) |
| DDNS + 路由器端口映射 | `http://nas.example.com:8765` |
| 域名 + 反向代理到 8765 | `https://sync.example.com`（Nginx 反代到 `127.0.0.1:8765`） |
| 文档示例网段直连 | `http://192.0.2.10:8765` |

FN Connect 中继通常**只转发飞牛系统端口**，不会转发自定义 8765；这种情况下桌面界面能正常用统一网关打开，但外网同步仍需上面几种方式之一。填了 HTTPS 自签证书的地址，需先在对应浏览器里访问一次并信任证书。

若只在家用，备用地址留空即可，行为与旧版一致。

## 五、安全设计

服务端鉴权只认 **Bearer 会话令牌**（或 HTTP Basic 的用户名密码），不依赖任何身份头或 Cookie 中的身份声明。网关对业务接口的额外要求是「转发前校验 NAS 登录会话」，这是飞牛网关层的行为，插件通过携带浏览器凭证（`credentials: 'include'`）复用已登录的飞牛会话来满足它。

| 场景 | 结果 |
| --- | --- |
| 网关通道 + 已登录 NAS + 有效应用令牌 | 正常访问 |
| 网关通道 + 未登录 NAS | 网关返回 `text/plain` 的 `invalid token`，请求到不了应用 |
| 直连通道 + 有效应用令牌 / Basic | 正常访问 |
| 直连通道 + 无令牌 | 401 |

`api/v1/setup/state` 在直连通道下不会下发任何敏感令牌；`config.json` 也不含令牌。

## 六、排障清单

| 现象 | 检查 |
| --- | --- |
| 网关图标打不开 | SSH 看 `$TRIM_PKGVAR/STARTUP_STATUS.txt`：应有「统一网关 Socket 已建立」。没有则看 `server.log` 是否报 Socket 绑定失败 |
| 网关图标报错、直连正常 | Socket 权限 / 所属组不允许网关进程访问；或 `gatewayPrefix` 与 `EB_GATEWAY_PREFIX` 不一致导致路由 404 |
| 网关页面白屏、接口 404 | 前缀没对齐：检查 `ui/config` 的 `gatewayPrefix` 与 `cmd/main` 的 `EB_GATEWAY_PREFIX` |
| 桌面能开、插件连不上 | 按管理端复制的配置填写；直连通道用 `http://<NAS-IP>:8765` |
| 插件在内网正常、外网失败 | 备用地址未达或 8765 未映射；设置页「测试连接」会显示命中通道 |
| 应用中心入口缓存了旧图标 | `sudo systemctl restart trim_app_center.service`，再 Ctrl+F5 刷新桌面 |

常用命令：

```bash
sudo cat /var/apps/edge-bookmarks/var/STARTUP_STATUS.txt
sudo tail -n 80 /var/apps/edge-bookmarks/var/server.log
ls -l /var/apps/edge-bookmarks/target/app.sock
curl -s http://127.0.0.1:8765/api/v1/setup/state   # 直连通道，应无敏感令牌字段
```

## 七、为什么没有自动声明 python312 依赖

官方支持在 `manifest` 写 `install_dep_apps=python312`，但依赖解析发生在**安装期**。实机排障已确认：安装期任何非确定性操作（检查 Python、创建目录、创建共享目录）失败，都会被应用中心笼统报成「无法创建应用程序目录」。因此保持 manifest 结构不变，`python312` 由用户在应用中心先行安装，风险更可控。

服务端启动脚本本身会依次查找 `/var/apps/python312/target/bin/python3`、`/usr/bin/python3`、`/usr/local/bin/python3` 和 `PATH`。
